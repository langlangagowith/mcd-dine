# 3 分钟路演稿骨架

> 目标：让评委在 3 分钟内相信「这个东西今天中午真的能用，而且它说的每个数都经得起追问」。
> 时间分配：30s 立问题 → 90s 现场跑一遍 → 60s 讲差异化与技术 → 30s 收尾。

---

### 0:00–0:30 立问题（不要自我介绍超过一句）

> 中午 11:50，三个人，人均 40，有人不吃牛肉。
> 你现在打开外卖 App，会看到 103 个商品、一堆套餐、几张券、满减规则——
> 然后你开始心算。算完还是不确定这单到底划不划算。

**一句话**：我做了一个输入「人数 / 预算 / 忌口」，直接给一桌搭配的配餐器。

### 0:30–2:00 现场跑（不要讲 PPT，直接跑）

1. **打开页面**（`python run.py` 或双击 `index.html`）
   - 指一下右上角：「实时 · MCP 已连接」。
2. **填参数**：3 人 / 人均 40 / 不吃牛肉 / 湖滨银泰 → 点「配这一桌」
   - 等待时念一句：这 5 秒里它在干嘛——「本地枚举了 2000 个组合，只对 6 个方案调了核价接口」。
3. **看第一张卡**：120.00 元，人均 40，用掉 100.0%
   - 指理由区：「这不是我编的，逐条念：菜单现价、核价结果、券池查过没有可用的券」。
4. **看第二张卡**：109.40 元，券省 10.60
   - 念那条：「11.9 元麦辣鸡腿堡（券 ID …8DDA65）挂到麦辣鸡腿汉堡：120.00 → 109.40，省 10.60 元」。
   - 补一句：这张券是**门店实时券池**里的，不是写死的活动页。
5. **点「证据链」**：门店券池 + 调用记录（工具名 / 耗时 / traceId）
   - 「每条都能对到麦当劳侧日志，评委可以抽查。」

> 如果时间富余：把人数从 3 改成 5，再点一次，让它现场重排——证明不是预生成的。

### 2:00–2:45 讲差异化（三句话，每句都要有对比）

1. **别人给建议，我们给依据**：每条推荐挂着真实价格与券号，不是"按经验配"。
   - 举例：券对「整行」生效这个坑（3 份汉堡挂 11.9 券接口只收 11.9），
     我们拆成「1 份带券 + 其余原价」，显示的 56.90 才是你实际要付的钱。
2. **预算是硬约束**：超一分都不给。券省下来的钱够一份小食，会自动加购再核一次。
3. **不让模型去试 35 个工具**：接口 600 次/分钟限流，组合在本地枚举，只核 Top-6。
   一次配餐 12~16 次调用、5~7 秒——这个数字就写在页面上。

### 2:45–3:00 收尾

> 它今天中午就能用：不套游戏外壳，不自动付款，建单前还会再核一次价。
> 代码、真实调用记录（带 traceId）、以及「三个踩过的坑」都开源在仓库里。

## 备用问答

**Q：为什么不做成小程序/App？**
A：比赛要「能打开能运行」。单文件 HTML 双击就能跑，评委不用装环境；连真数据只要 `python run.py`。

**Q：券是真的吗？价格是真的吗？**
A：全部来自麦当劳 MCP。`docs/evidence/2026-10-22-live-calls.md` 里有券 ID、券码、traceId 和券前券后原始分值。

**Q：门店打烊了怎么办？**
A：如实报「06:00-21:00，此刻不在营业」，并列出附近还营业的店——不给你一个算不出来的方案。

**Q：忌口怎么保证？**
A：名称+标签先过滤；对组成不明的套餐再调 `query-meal-detail` 核实；结果里写明判定来源。
不承诺过敏级安全（麦当劳没有公开配料表）。

**Q：为什么只有 6 个方案？**
A：前 6 个已经覆盖"最合预算 / 券省最多 / 不同主食"三类取向；再多就是同一桌换个饮料凑数。
